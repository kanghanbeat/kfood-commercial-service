## 🟡 향후 개발 계획 — 데이터 증가 대비 확장성 정비 (2026-07-24, 지금은 보류)

**결정:** 현재 서비스의 발전 순서는 `어드민 운영 안정화 → 콘텐츠·사진 생산 → 공개 페이지·SEO(검색 노출 최적화) → 수익화`로 유지한다. 지금 데이터 규모에서는 전면 재설계보다 콘텐츠 생산과 공개 화면 개선이 우선이므로, 아래 작업은 즉시 구현하지 않고 착수 조건이 생길 때 단계적으로 진행한다.

**현재 판단:** Next.js(웹 애플리케이션 틀) + Supabase(데이터베이스·인증·파일 저장 서비스) 구조는 계속 사용할 수 있다. 다만 현재 일부 목록·검색은 데이터 전체를 서버로 가져온 뒤 메모리에서 필터링하거나 페이지를 나누므로, 항목이 수백~1,000건을 넘기 시작하면 응답 속도·메모리 사용·조회 누락 위험이 커진다. 사진 저장은 데이터베이스와 파일 저장소가 한 번에 처리되지 않고, 여러 관리자가 같은 항목을 편집할 때 덮어쓰기 방지도 아직 없다.

**선택한 방향:** 최소 제한만 두는 임시 대응, 서비스를 전면 분리하는 대규모 재설계, 현재 구조를 유지하며 병목부터 단계적으로 고치는 세 가지를 비교했고, 세 번째인 **단계적 확장**을 채택한다. 지금은 마이크로서비스(기능별로 서버를 여러 개 분리하는 구조), 외부 검색엔진, 전면 재작성은 도입하지 않는다.

### 1단계 — 항목 수 1,000건에 가까워지기 전에 필수

- 목록 조회를 DB 페이지 나누기(데이터베이스에서 필요한 구간만 가져오기)와 서버 쪽 검색·상태 필터로 전환
- 공개 음식·장소·지역·루트 목록에 조회 개수 제한과 페이지 나누기 적용
- 통합 검색을 전체 데이터 메모리 필터 방식에서 DB 검색 방식으로 전환
- 콘텐츠 삭제 시 사진 DB 기록과 Storage(파일 저장소) 파일이 함께 정리되는지 보장
- 사진·사이트 설정 관련 마이그레이션(데이터베이스 구조 변경 기록) `013~015`가 운영 환경에 적용됐는지 확인

### 2단계 — 관리자 동시 작업·대량 작업이 늘기 전에

- `updated_at`(마지막 수정 시각)을 이용한 낙관적 잠금(다른 관리자의 최신 수정을 실수로 덮어쓰지 않게 하는 검사) 추가
- 일괄 변경을 RPC/트랜잭션(여러 DB 변경을 전부 성공하거나 전부 취소하는 처리)으로 전환
- 사진 대표 지정·순서 변경을 한 번에 안전하게 저장하고, 주인 없는 사진 기록·파일을 점검하는 정리 작업 추가
- 촬영 달력은 전체 자료 대신 선택한 날짜 범위만 조회

### 3단계 — 공개·SEO 페이지가 수천~수만 개로 커질 때

- 사이트맵(sitemap — 검색엔진에 페이지 목록을 알려주는 파일)을 여러 파일로 분리
- 자주 쓰는 검색 조건에 FTS/trigram 인덱스(긴 글·부분 단어 검색을 빠르게 하는 DB 색인) 적용
- 캐시·재검증(자주 바뀌지 않는 결과 재사용)과 성능 관측 지표 추가
- 비대해진 `packages/data/src/index.ts`를 기능별 모듈(역할별 코드 묶음)로 분리

**착수 기준:** 한 종류의 항목이 약 500건이면 성능을 측정하고 1단계를 준비한다. 1,000건에 가까워지면 1단계를 새 기능보다 먼저 처리한다. 한 번에 50건 이상을 바꾸거나 관리자 3명 이상이 동시에 작업하면 2단계를 시작한다. 공개 주소가 10,000개를 넘거나 사이트맵 생성이 느려지면 3단계를 시작한다.

세부 실행 목록은 `docs/06-team/백로그.md`의 "데이터 확장 대비"에서 관리한다.

### 🟢 어드민 목록 개선 + 어드민 로그인 풀림 재발 해결 (2026-07-22, 세션13) — 프리뷰 검증 완료

**1) 어드민 목록 개선 (1순위 작업)**

어드민 화면을 점검한 결과: 지역·음식·루트·촬영은 생성+수정, 장소는 수정만, 신고·게시물·댓글은 상태 변경까지 실제 DB에 붙어 있으나, 인사이트·콘텐츠 제작 화면 전체와 상단 숫자 카드 8개는 정적 파일/하드코딩. 목록 8개가 **전건을 편집 폼 펼친 채로 한 페이지에 나열**해서 음식 50개·장소 30+에서 이미 쓰기 힘든 상태였다.

- `web/components/admin/list-controls.tsx` 신규 — 검색·상태 필터·페이지 계산(`applyListParams`), 도구 모음, 페이지 이동, 접히는 항목을 공통 제공
- 목록 8개(지역·음식·장소·루트·촬영·신고·게시물·댓글)에 동일 적용. 한 페이지 20건, 항목은 기본 접힘
- 항목별 공개 페이지 미리보기 링크(새 탭). 촬영 콘텐츠는 외부 채널 URL
- 저장 후 `return_query`로 검색·필터·페이지 상태 유지

**2) 어드민 로그인 풀림 — 세션9 원인의 어드민 버전 + 회귀**

증상: 어드민 로그인 후 다른 메뉴로 이동하면 `/admin/login?next=…`로 튕김. (`next=`가 붙는다 = proxy 게이트가 쿠키 없음으로 판단한 것 = 쿠키가 실제로 지워졌다는 신호. 검증 실패라면 `next=` 없이 `/admin/login`만 뜬다 — 다음에도 이 구분으로 먼저 좁힐 것.)

원인 2가지가 겹쳐 있었다.
1. `getAdminSession()`이 **화면 렌더 중에** `refreshSession()`을 호출 — Supabase는 갱신 때마다 리프레시 토큰을 교체하고 옛 토큰을 폐기하는데, 렌더 중에는 쿠키를 쓸 수 없어 `cookies().set()`이 실패하고 `catch {}`로 삼켜졌다. 브라우저에는 이미 폐기된 토큰이 남고, 다음 이동에서 proxy가 그 죽은 토큰으로 갱신 시도 → 실패 → 쿠키 삭제. **세션9에서 공개 세션에 대해 잡았던 것과 같은 원인의 어드민 버전.**
2. 세션9의 해결책이었던 **`autoRefreshToken: false`가 세션10 인증 재작성(`72daa0c`) 때 코드에서 통째로 사라져 있었다** — 저장소 어디에도 없었다. 문서에는 "핵심 수정"으로 남아 있는데 코드에서만 유실된 회귀.

수정:
- `getAdminSession()`을 읽기 전용으로. 토큰 갱신·쿠키 삭제는 `proxy.ts`만 담당
- 그 경로에서만 쓰이던 `setAdminAuthCookies`/`clearAdminAuthCookies`/`createSupabaseRefreshClient` 제거 (재발 방지)
- 어드민 Supabase 클라이언트 2곳에 `autoRefreshToken: false` 복원
- 어드민 링크 `prefetch={false}` — 여러 요청이 동시에 갱신을 시도하면 리프레시 토큰이 서로를 무효화한다

**검증:** 프리뷰 배포(`feature/admin-list-controls`)에서 솔이 로그인 → 메뉴 이동 반복 → 로그아웃 안 됨 확인.

**공개 세션 점검 결과 (같은 세션에서 확인):** 처음엔 "공개 세션에도 같은 회귀가 있다"고 판단했으나 **틀렸다.** `@supabase/ssr` 0.12.0의 `createServerClient`는 내부에서 `autoRefreshToken: false`를 강제한다(사용자 옵션보다 뒤에 병합돼 덮어씀). 세션10에서 이 설정을 코드에서 뺀 것은 유실이 아니라 **라이브러리가 보장하게 됐기 때문**이었다. 공개 세션 읽기 경로(`getPublicSession`)에도 명시적 `refreshSession()` 호출이 없다.

다만 `createPublicSupabaseUserClient`는 `@supabase/ssr`가 아니라 supabase-js `createClient`를 직접 써서 기본값이 true였으므로, 어드민과 일관되게 `autoRefreshToken: false`를 명시했다(세션을 저장하지 않아 실질 위험은 낮았음 — 방어적 조치).

**어드민에서 실제로 증상을 만든 것은 `autoRefreshToken`이 아니라 `getAdminSession()`의 명시적 `refreshSession()` 호출이었다.**

**진행 중 사고 기록:** 작업 도중 Next.js 16에서 미들웨어 파일 이름이 `middleware.ts` → `proxy.ts`로 바뀐 걸 놓치고 `middleware.ts`를 새로 만들어, "둘 다 있으면 안 된다" 에러로 로컬 개발서버가 15분쯤 전면 404 상태였다(삭제 후 복구). **이 저장소의 미들웨어는 `web/proxy.ts` 하나뿐이다.**

**프리뷰 주소 안내 실수:** 브랜치를 푸시한 뒤 프리뷰 주소를 알려주지 않아, 솔이 옛 배포(`…git-feature-482093…`)에서 계속 테스트했다. 브랜치별 프리뷰 주소는 서로 다르다 — 푸시 후에는 `gh api repos/…/deployments` → `…/statuses`의 `environment_url`로 실제 주소를 확인해서 전달할 것.

## 개발 환경 메모

- ⚠️ **`.env.local`이 두 곳에 있음 — 실제로 적용되는 건 `web/.env.local`**. 루트(`kfood-commercial-service/.env.local`)에 넣어도 Next.js는 안 읽는다(앱이 `web/` 워크스페이스에 있어서). 환경변수는 항상 `web/.env.local`에 넣을 것 (2026-07-07 실제로 이 문제로 헤맴)
- `web/.env.local`: `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_ANON_KEY`(2026-07-07 연결 완료) + `NEXT_PUBLIC_ALLOW_ALPHA_FALLBACK=true`(Supabase 실패 시 fallback 허용, gitignore됨)
- `ADMIN_PREVIEW=true`를 `web/.env.local`에 추가하면 로그인 없이 로컬에서 `/admin`·`/mypage` 열람 가능(개발용, `NODE_ENV` 가드로 프로덕션 무효). **단, 이건 진짜 로그인이 아니라 가짜 토큰이라 실제 Supabase 쓰기(저장)는 안 됨** — 저장 기능 테스트하려면 실제 admin/editor 계정으로 로그인해야 함. 확인 끝나면 반드시 제거할 것
- `npm install`은 시스템 npm 캐시 권한 문제로 `npm install --cache <임시경로>` 필요할 수 있음
