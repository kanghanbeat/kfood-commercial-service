## 0. 이번 갱신의 성격 — 두 기획의 통합 업그레이드

이 갱신은 어느 한쪽 기획으로 바꾼 것이 아니라, **솔의 초기 기획 + 한빛의 기획 + 한빛이 실제 구축해 둔 것**을 놓고 "현재 목표(SNS→유입→수익화)에 무엇이 가장 잘 작동하는가" 기준으로 정리한 결과다. 각 변경의 배경:

| 변경 | 무엇을 보완하기 위해 |
|---|---|
| 콘텐츠 사이트 집중 + 커뮤니티·도감 후순위 | 기존 결정이 대부분 "병행"이어서 두 기획의 기능을 동시에 만들다 작업이 복잡해지고 충돌이 생겼음. 도감·챌린지를 검증 후로 미루자는 한빛의 원안과, 실행하며 확인된 운영 부담(로그인·모더레이션)을 반영해 **집중 순서를 정한 것**. 한빛이 구축한 커뮤니티는 삭제·동결이 아니라 후순위 — 기능은 유지하고, 노출 여부는 어드민 공개/비공개 토글로 운영에서 결정. 트래픽 확보 후 개발 재개 |
| 3카테고리 IA + 음식×지역 URL 구조 | 메뉴가 6개(음식/지역/장소/루트/피드/검색)로 분산되어 방문자 동선이 복잡했음. 한빛이 만든 DB 구조(장소-음식-지역 태그)가 이미 이 구조를 지원하므로 **재개발이 아니라 내비게이션·템플릿 수준의 재배치**이며, 음식×지역 조합 페이지가 롱테일 검색 유입구가 됨 |
| SVG 지도 메인 | 유료 지도 API(월 과금·카드 등록) 없이 0원으로 구현 가능하고, 브랜드 디자인 자유도와 SEO(지도 안 콘텐츠는 검색 노출 안 됨)에서 유리. 한국관광데이터랩·일본 TABERUKOTO에서 검증된 포맷 |
| AI 경로 추천 후순위 | 호출당 과금되는 변동비 구조 + 비로그인 개방 시 봇 악용 위험. 한빛이 구축한 루트 가이드를 저장 데이터와 매칭하는 방식으로 같은 가치를 먼저 제공하고, AI는 수익 발생 후 조건부 도입 |
| 역할·프로세스 재정리 | 두 사람이 같은 파일을 동시에 수정하다 충돌(PR #1)이 발생했고 리뷰 대기가 병목이 됐음. 각자 강점에 맞게 — 솔은 실행 속도, 한빛은 구조·보안 검토와 화면 검수 — 로 재배치해 충돌 지점 자체를 없애는 방식 |

**용어 정리 — "상세페이지":** 대화에서 서로 다른 의미로 쓰여 혼선이 있었음. 이 서비스의 음식·장소 페이지는 장마다 따로 제작하는 페이지가 아니라 **템플릿 1개 + DB 데이터로 자동 생성되는 "개별 페이지"** (템플릿 파일 하나를 고치면 50개 페이지가 한꺼번에 바뀌는 구조). 앞으로 "상세페이지 만든다" 대신 **"데이터를 추가한다"(페이지가 늘어남) / "템플릿을 고친다"(전체 반영)**로 구분해 부른다.

## 1. 방향 결정 (2026-07-08)

### 1-1. 앞으로 3개월 집중: 콘텐츠 사이트

- **수익 로드맵**: SNS 채널 → 홈페이지 유입 → 구글 애드센스 → 팔로워 성장 후 광고·협찬.
  - 애드센스는 트래픽 확보 단계의 보조 수익 (여행 니치 기준 1,000뷰당 $5~20 수준 — 큰 수익원이 아님을 전제)
  - 본 수익은 채널이 큰 뒤의 광고·협찬. 따라서 초기 목표는 수익이 아니라 **유입량과 콘텐츠 품질**
- 이 목표에 필요한 것은 "검색·SNS에서 들어와 정보를 잘 읽고 가는 빠른 콘텐츠 사이트"가 전부다.
- **후순위 영역** (삭제·동결 아님 — 기능은 유지하되, 신규 개발·확장을 콘텐츠 사이트 뒤로 미룸):
  - 커뮤니티 피드·댓글·신고·모더레이션
  - 푸드도감·트래커·인포그래픽·여정 공유
  - 마이페이지는 "저장한 맛집 모아보기"로 최소화
- **노출 여부는 기획이 아니라 운영에서 결정**: 모든 게시판을 어드민에서 공개/비공개 토글로 관리할 수 있게 구축하고(커뮤니티 카테고리 토글은 이미 있음 → 전체 게시판으로 확대), 상황에 따라 열고 닫는다
- 콘텐츠 채우기는 API·AI를 활용해 속도를 내되, 발행 순서는 **AI·데이터 초안 → 사람 검수·큐레이션 → 발행**을 지킨다 (대량 자동 생성 콘텐츠는 애드센스·검색 정책상 불이익이 있고 큐레이션 신뢰를 훼손하므로)
- 트래픽과 애드센스가 자리잡으면 후순위 기능의 개발·확장을 재개한다.

### 1-2. 포지셔닝

> **"비짓서울의 '음식' 카테고리만 떼어내서 전국판으로 만든, K푸드·로컬푸드 특화 큐레이션 서비스"**

- 벤치마크 1 — **비짓서울** (korean.visitseoul.net): 큐레이션 문법을 가져온다 — 계절 테마 히어로, 에디터 픽, 테마 코스, 대형 이미지 카드, 매거진처럼 읽히는 톤.
  단, 범위는 따라가지 않는다 (실시간 가이드·도보해설·앱·개인화 추천 등은 대상 아님)
- 벤치마크 2 — **한국관광데이터랩 지도** (datalab.visitkorea.or.kr): 시·도별 색칠 지도(SVG) 방식을 메인 입구로 가져온다
- 지도 검색형 서비스(거지맵 등)와는 다른 제품 — 우리는 검색이 아니라 큐레이션
- **글로벌 레퍼런스 조사 결과 (2026-07-08)**: 동일 모델의 한국 대상 서비스는 부재. 일본에는 완성형(byFood, JTB 투자)이 존재해 시장성 검증됨. 상세: `벤치마크-레퍼런스.md`

### 1-3. 정보 구조 (IA) — 3카테고리

```
음식 (Food)     ← 1순위. 비로그인·SEO·애드센스의 본체
커뮤니티        ← 이미 구현됨. 노출만 유지, 확장 보류
마이페이지      ← "저장한 맛집 모아보기"로 최소화
```

- 지역·장소·루트는 별도 메뉴가 아니라 **음식 카테고리 안의 탭·필터**로 정리
- **탭은 반드시 각자 URL을 갖는다** (JS 탭 금지 — 검색 색인·SNS 딥링크 필요):
  ```
  /foods/tteokbokki          떡볶이 소개 + 전체 맛집
  /foods/tteokbokki/seoul    서울 떡볶이 맛집  ← "best tteokbokki in Seoul" 롱테일 검색 유입구
  /foods/tteokbokki/busan    부산 떡볶이 맛집
  ```
- 음식×지역 조합 페이지 하나하나가 검색 유입구가 된다 (외국인 실제 검색어는 롱테일)

### 1-4. 메인 화면 — 4섹션 고정

```
① 히어로       계절/테마 큐레이션 1장 (예: Summer Naengmyeon Guide, 분기마다 교체)
② 한국 지도    SVG 시·도 지도, 지역 클릭 → 지역 페이지 (브랜드 팔레트)
③ 카드 섹션    트렌딩 음식 / 에디터 픽
④ 채널 연동    From our channels (우리 SNS·유튜브 콘텐츠)
```
- 4개 섹션을 넘기지 않는다.

### 1-5. 지도 구현 방식

| 용도 | 방식 | 비용 |
|---|---|---|
| 메인 한국 지도 | **SVG 일러스트 지도** (공공 시·도 경계 데이터 사용). 색칠 기준 = 콘텐츠 밀도 또는 "지금 뜨는 지역". 마우스오버 시 지역명+대표 음식 툴팁, 클릭 시 지역 페이지 이동 | 0원 |
| 개별 맛집 위치 | 구글맵 임베드(iframe) 또는 "Open in Google Maps" 딥링크 | 0원 |
| 지역별 맛집 리스트 공유 | 우리 구글 계정으로 **구글맵 저장 리스트** 생성 → 공유 링크를 페이지에 버튼으로 게시 ("Save this list to your Google Maps") | 0원 (운영으로 해결) |
| 유료 지도 API (Google Places, 지도 JS API 등) | **도입하지 않음.** 장소 데이터는 직접 큐레이션 (에디토리얼 정체성과 일치) | — |

- 외국인 타겟이므로 지도 연동은 카카오·네이버가 아닌 **구글맵** 기준 (여행자가 현지에서 실제로 쓰는 앱)
- 한국관광데이터랩의 지역별 방문자·지출 데이터는 무료 다운로드 가능 → 추후 "이번 달 외지인이 많이 찾은 지역" 같은 콘텐츠 근거로 활용 (API 불요)

### 1-6. AI 경로 추천 — 후순위 확정

- **1단계 (지금)**: 이미 있는 루트 가이드를 저장 데이터와 단순 매칭해 노출 ("저장한 맛집이 이 지역에 몰려 있어요 → 이 루트를 보세요"). API 비용 0
- **2단계 (트래픽·수익 발생 후)**: AI 안내 도입. 전제 조건 3가지 —
  ① 로그인 사용자 한정 ② 하루 호출 횟수 제한 ③ 결과 캐싱(같은 조합 재사용)
- 근거: AI 호출은 건당 몇 원 수준(Haiku 기준 약 6원/회)이지만 트래픽 비례 변동비 + 봇 악용 위험이 있어, 수익 발생 이후로 미룬다

월요일        이번 주 할 일 3개 이하를 슬랙에 공유, 한빛 확인

## 5. 한빛 확인 안건 (2026-07-09 승인 완료)

한빛 검토 결과: 아래 5개 안건 모두 승인. 2주차 지도 작업의 시·도↔지역 매핑은 **A안(코드 매핑표, 스키마 무변경)** 으로 확정한다. B안(`regions.province` 필드 추가)은 스키마 변경이므로 필요성이 생길 때 별도 high-risk 승인으로 재검토한다.

1. **§1-1 방향**: 3개월 콘텐츠 사이트 집중, 커뮤니티·도감·트래커는 후순위 (어드민 공개/비공개 토글로 노출 관리) — **O**
   - 참고: 도감·챌린지를 검증 후로 미루자는 것은 한빛이 먼저 제안했던 방향으로, 이번 결정은 그 방향으로 정렬하는 것
2. **§1-3~1-5 구조**: 3카테고리 IA, 메인 4섹션, SVG 지도 방식 — **O**
   - 함께 결정: 지도(시·도 17개)와 지역 데이터(동네 단위 23개)의 연결 방식은 **A안(코드 매핑표, 스키마 무변경)** 으로 확정. 상세: `메인개편-작업계획.md`
3. **§3 역할 분담**: 솔 주도 개발 + 한빛 보안·유지보수·검수 — **O**
4. **§4 프로세스**: 주간 루프로 통일 (PDCA vs Sprint 논의 종결) — **O**
5. **§2 비용**: 애드센스 시점 Vercel Pro 전환 — **O / 사전 공유 완료**

### 5-1. 안건별 상세 설명

**안건 1 — 3개월 집중 방향**
- **결정할 것**: 앞으로 3개월은 음식·지역·장소·루트 콘텐츠 페이지의 품질·개수·속도에 우선 투자하고, 커뮤니티·푸드도감·트래커·인포그래픽은 **후순위**로 둔다 (개발·확장을 미루는 것이지 삭제·동결이 아님). 노출 여부는 모든 게시판에 어드민 공개/비공개 토글을 갖춰 운영에서 결정
- **왜**: 우리 수익 계획(SNS→유입→애드센스→협찬)에 지금 필요한 건 "비로그인 방문자가 정보를 잘 읽고 가는 빠른 사이트"가 전부. 그동안 결정이 대부분 "둘 다 하자(병행)"여서 기능 두 벌을 동시에 만들다 작업이 꼬였음. 우선순위를 정하면 개발 리소스가 유입에 직결되는 곳에만 쓰임
- **한빛 입장**: 한빛이 만든 커뮤니티(피드·댓글·신고)는 코드·DB 그대로 유지. 공개/비공개는 어드민 토글로 언제든 조정 가능하고(카테고리 토글은 이미 구현됨 → 전체 게시판으로 확대), 트래픽이 생기면 개발 재개
- **콘텐츠 속도**: 페이지 채우기는 API·AI로 속도를 내되, 발행은 "초안 자동 생성 → 사람 검수·큐레이션 → 발행" 순서 유지 (대량 자동 생성 콘텐츠는 애드센스·검색 정책 불이익 위험)
- **예상 질문**: "커뮤니티 개발은 언제 재개?" → 회의에서 재개 기준(예: 월 UV 1만 또는 애드센스 승인 시점)을 같이 정하면 이 문서에 추가

**안건 2 — 사이트 구조 (3카테고리·메인 4섹션·SVG 지도)**
- **결정할 것**: ① 내비게이션을 6개(음식/지역/장소/루트/피드/검색)에서 3개(음식/커뮤니티/마이페이지)로 줄이고 지역·장소·루트는 음식 안의 탭으로 (단, 탭마다 URL을 가져 `/foods/tteokbokki/seoul` 같은 검색 유입구 확보) ② 메인 화면은 히어로/SVG 한국 지도/트렌딩·에디터 픽/SNS 콘텐츠 4섹션 고정 ③ 지도는 유료 API 없이 SVG 지도 + 무료 구글맵 임베드·딥링크 + 우리 구글 계정의 저장 리스트 공유로 구현
- **왜**: 방문자 동선 단순화 + 검색 유입 극대화 + 비용 0 유지. 벤치마크 근거: 같은 모델의 일본 서비스(byFood)가 투자받으며 성장했고, 클릭형 지도는 일본 TABERUKOTO에서 검증된 포맷인데 한국 대상 영어 서비스는 없음 (상세: `벤치마크-레퍼런스.md`)
- **한빛 입장**: **재개발이 아님.** 한빛이 설계한 DB(장소-음식-지역 태그 구조)가 이 그림을 이미 지원해서, 바뀌는 건 내비게이션과 페이지 템플릿뿐. 스키마 변경 없음
- **예상 질문**: "SEO 순위 떨어지지 않아?" → 기존 URL(`/foods/...`, `/regions/...`)은 유지되고 조합 페이지가 추가되는 방향이라 기존 색인에 손해 없음

**안건 3 — 역할 분담**
- **결정할 것**: 솔 = 기획·개발·콘텐츠·배포 실행 / 한빛 = 방향 검토 + 보안·유지보수. 한빛의 구체적 담당은 ① DB 스키마·RLS(권한)·프로덕션 환경변수 변경 승인 ② 월 1회 관리자 계정·감사 로그 점검 ③ PR마다 미리보기 화면 검수
- **왜**: 두 사람이 같은 파일을 고치다 실제로 충돌(PR #1)이 났고, 리뷰 대기가 병목이 됐음. 역할이 겹치지 않게 재배치하면 충돌 지점 자체가 사라짐. 각자 강점 배치이기도 함 — 실행 속도는 솔, 구조·보안 판단은 한빛
- **한빛 입장**: 코드를 줄 단위로 읽는 부담이 없어짐. PR마다 Vercel이 자동 생성하는 미리보기 링크를 폰에서 열어 "기획 의도대로 나왔나"만 보면 되고, 대신 서비스가 뚫리면 안 되는 지점(스키마·권한·환경변수)은 한빛 승인 없이 변경 불가 — 전체 그림과 안전장치를 쥐는 역할
- **예상 질문**: "내가 개발에서 빠지는 건가?" → 아니다. high-risk 영역(DB·보안)의 결정권이 한빛에게 있고, 원하면 언제든 코드 작업도 가능. 기본값이 바뀌는 것뿐

**안건 4 — 진행 프로세스**
- **결정할 것**: 미결로 남아 있던 "PDCA 9단계 vs Sprint" 논의를 끝내고 주간 루프로 통일 — 월요일 할 일 3개 이하 슬랙 공유 → 주중 솔이 브랜치 개발 → PR 미리보기로 한빛 검수 → 머지·자동 배포. 규칙: 같은 주에 같은 폴더를 둘이 동시에 수정하지 않는다
- **왜**: PDCA도 Sprint도 큰 팀용 방법론이라 2인 팀에는 관리 비용이 실작업보다 커짐. 위 루프는 이미 쓰고 있는 도구(슬랙·GitHub·Vercel·session-handoff.md)만으로 돌아감
- **예상 질문**: "급한 건은?" → high-risk가 아니면 주중에도 그냥 PR로 진행, 월요일 리스트는 우선순위 합의용이지 승인 절차가 아님

**안건 5 — 비용 (사전 공유)**
- **알릴 것**: 이건 동의보다 사전 공지. 지금은 월 $0(Supabase Free + Vercel Hobby)인데, **Vercel 무료 플랜은 상업적 이용 금지 조건**이 있어 애드센스를 붙이는 순간 Pro($20/월)로 올려야 규정에 맞음. 성장하면 Supabase Pro($25) 포함 월 $45~75 수준
- **함께 공유**: Google Places API(월 $200으로 잡혀 있던 항목)는 도입하지 않기로 함 — 지도는 전부 무료 방식(SVG+임베드+리스트 공유)으로 해결. AI 경로 추천도 변동비 문제로 후순위 — 지금 있는 루트 가이드 매칭으로 먼저 감
- **예상 질문**: "$20 언제부터?" → 애드센스 승인 신청 시점. 그 전까지는 0원 유지
