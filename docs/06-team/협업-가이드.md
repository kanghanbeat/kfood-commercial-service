## B. 슬랙 — 단일 채널 + GitHub 자동 알림

- **채널 하나로만 소통.** (텔레그램·카톡 업무방 따로 안 만든다 — 흩어지면 놓친다)
- **GitHub 알림을 그 채널에 연동**한다. push·PR·머지·이슈가 자동으로 흘러오게.
  - 연동: GitHub 저장소 → Settings → Integrations, 또는 슬랙 GitHub 앱에서 `/github subscribe kanghanbeat/kfood-commercial-service`
  - 받을 이벤트: `pulls`, `commits`(main), `issues`, `releases`
- **말로 할 것 / 알림이 대신할 것 구분**:
  - 알림이 대신함 → "올렸다", "PR 열었다", "머지됨" (굳이 타이핑 X)
  - 사람이 말함 → "나 오늘 OO 크게 손볼게", "이 PR 봐줘", 막힌 결정
- 한빛이 대표 결정자 → **방향이 갈리면 슬랙에서 한빛이 콜.**

## C. Git 루틴 (충돌·사고 막는 핵심)

새 본진은 **PUBLIC + Vercel 라이브**다. main이 곧 서비스이므로 직접 못 건드린다.

### 규칙 4개

1. **작업 전 받기** — 항상 최신 main을 받고 시작 (`git pull`)
2. **브랜치에서 작업** — `feature/`, `fix/`, `docs/`, `content/` 접두어 (한빛 CONTRIBUTING 기준)
   - 예: `docs/collab-guide`, `content/seoul-place-corrections`, `feature/insight-dashboard`
3. **main 직접 수정 금지** — 무조건 **PR**로 올리고, 상대가 한 번 본 뒤 머지
4. **작게 자주** — 한 덩어리 끝나면 바로 commit + push. 며칠 묵히지 않는다

**PR 올리기 전 (한빛 규칙 — 원본은 저장소 `CONTRIBUTING.md`):**
- `npm run check` · `npm run web:build` 통과 (못 돌리면 PR에 이유 적기)
- `.github/pull_request_template.md` 양식대로 작성 (무엇/왜/검증/스크린샷/마이그레이션·env 영향)
- **High-risk**(RLS·admin 인증·Supabase 마이그레이션·prod env·발행 로직)는 **한빛(owner) 명시 승인 필수**

### 솔은 명령어 외울 필요 없다

Claude Code에게 말로:
> "새 브랜치 파서 작업 시작해줘" / "지금까지 한 거 올리고 PR 열어줘" / "한빛 PR 받아줘" / "충돌 정리해줘"

### 흐름

```
받기(pull main) → 브랜치 → 작업 → commit/push → PR → 상대 확인 → 머지 → 브랜치 삭제
```

> ⚠️ git은 실시간 동기화(구글닥스)가 아니다. **PR이 머지될 때만** 합쳐진다.

## E. AI 바이브코딩 협업 규칙

도구가 둘(솔=Claude Code / 한빛=Codex)이라 **규칙을 한 곳에 모은다.**

### 1) 헌법 동기화 — CLAUDE.md ↔ AGENTS.md

- 프로젝트 규칙의 **원본은 `AGENTS.md` 하나**. Codex가 읽는다.
- `CLAUDE.md`는 `@AGENTS.md` import로 **같은 헌법을 그대로 참조**한다. 규칙을 양쪽에 중복 작성하지 않는다.
- 규칙이 바뀌면 `AGENTS.md`만 고친다 → 두 도구가 자동으로 같은 기준을 본다.

### 2) AI 작업 폴더 범위 지정

각 AI가 **건드려도 되는 폴더를 명시**해 의도치 않은 광역 수정을 막는다.

| 도구 | 기본 작업 범위 | 손대기 전 한마디 필요 |
|---|---|---|
| Claude Code (솔) | `docs/`, 콘텐츠, 디자인 토큰, 데이터 JSON | `web/` 코어 로직, `supabase/` 스키마 |
| Codex (한빛) | `web/`, `supabase/`, `packages/`, `.codex/` | `docs/` 기획 문서 대량 수정 |

→ "벽"은 아니지만, **범위 밖을 크게 건드릴 땐 슬랙 한 줄**(§B)이 규칙.

### 3) 디자인 토큰은 고정값

- 토큰 원본: **`docs/02-design/DESIGN.md` (v2)** + `docs/02-design/globals.css`
- 현재 팔레트: brand `#8500FF` / accent `#FF5E00` / 배경 흰색 — **임의 변경 금지**
  - ⚠️ 옛 문서의 `#4D2475`는 v1 잔재. **DESIGN.md v2가 기준.**
- 폰트: **Pretendard 로컬 woff2** (CDN 금지)
- 사용자향 카피는 **영어 우선**, 발행 전 영문 검수 통과

### 4) 표준 용어 풀이 — 솔·한빛 공용 (2026-07-17 추가)

AI(Claude Code·Codex)가 개발 용어를 쓸 때는 **항상 "용어(쉬운 설명)" 형식**으로 풀어 쓴다 — 요청하지 않아도, 대화·문서·보고서 전부. 두 사람이 같은 풀이를 쓰도록 자주 나오는 용어는 아래 표준을 그대로 사용한다:

| 용어 | 표준 풀이 |
|---|---|
| 커밋 | 내 컴퓨터에 저장 지점 기록 |
| 푸시 | 커밋한 것을 깃허브에 업로드 |
| 머지 | 작업 브랜치의 변경사항을 실제 서비스 버전에 합쳐 넣는 것 |
| 브랜치 | 원본을 건드리지 않는 작업용 복사본 |
| PR(풀 리퀘스트) | 브랜치 작업을 검토받고 머지해달라는 요청서 |
| 배포 | 코드를 실제 서비스 주소에 반영하는 것 |
| 프리뷰 배포 | 머지 전 브랜치 상태를 미리 볼 수 있는 임시 주소 |

## F. 콘텐츠 모델 — `productions`(제작 콘텐츠) vs `user_posts`(커뮤니티 UGC)

병합 후(§8 완료9) 두 테이블이 헷갈릴 수 있어 정리(2026-07-06). **스키마 합치지 않음 — 소유자·검수 경로가 달라서 독립 유지가 맞음.**

| | `productions`(솔, 008) | `user_posts`(한빛, 007) |
|---|---|---|
| 누가 쓰나 | 어드민/에디터만 (콘텐츠 관리 "촬영" 탭) | 공개 사용자 (로그인 후 작성) |
| 무엇인가 | 우리가 직접 만든 영상·블로그·릴스 (공식 콘텐츠) | 사용자가 남긴 기록·후기 (UGC) |
| 검수 | `publication_status`(초안/공개/숨김/보관), 에디터가 발행 | `pending_review → published`, 어드민이 모더레이션 (5-1에서 운영 탭에 편입) |
| 참조 연결 | `production_tags`(지역/음식/장소/루트, 다대다) | `user_posts.region_id/food_id/place_id/route_guide_id`(단일 FK) |
| 지금 노출 위치 | 어드민 내부만 (공개 페이지 아직 없음 — §10 2-3 예정) | `/feed` 공개 |

**결정**: 합치지 않고 각자 역할 유지. 지역/음식 상세페이지에 콘텐츠를 노출할 때(§10 2-3)도 "공식 제작 콘텐츠" 섹션과 "커뮤니티 게시물" 섹션을 **분리해서** 보여준다(배지로 구분: 공식 vs 사용자). 어드민에서도 이미 분리되어 있음(콘텐츠 관리 > 촬영 / 운영 > 게시물·댓글 관리, 5-1 완료).

**한빛과 확인할 것**: 커뮤니티(UGC)를 제품 방향으로 계속 키울지는 아직 열린 질문(`기획정렬-한빛대조.md` §4-3). 이 정리는 "지금 스키마를 어떻게 둘지"에 대한 기술 판단이고, "커뮤니티를 얼마나 키울지"는 별개의 방향 결정임 — 스키마 정리가 그 결정을 대신하지 않음.
